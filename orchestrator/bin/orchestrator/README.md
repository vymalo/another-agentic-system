# orchestrator (binary)

The orchestrator service: the composition root that wires the Postgres store,
the A2A adapter (and, with the feature `agent-local`, the local agents), the dispatcher, the inbox worker, the resource API and the interaction surfaces
chosen by `ORCH_SURFACES` into one stateless process. `ORCH_ROLE` says which
halves the process runs: the control plane, a worker, or both
([ADR 0015](../../../docs/decisions/0015-control-plane-and-workers-on-adam-rs.md)).

## Where it sits

The only crate that depends on every adapter, and the only place that chooses
implementations
([ADR 0009](../../../docs/decisions/0009-swappable-implementations-at-build-time.md)):
[`orch-store-postgres`](../../crates/store-postgres/README.md) for
`ThreadStore` and `Wakeup`, [`orch-agent-a2a`](../../crates/agent-a2a/README.md)
for `AgentClient` (and, with the feature `agent-local`, [`orch-agent-adam`](../../crates/agent-adam/README.md) for
in-process agents, routed by transport with `ByTransport`), [`orch-artifacts-fs`](../../crates/artifacts-fs/README.md) and
[`orch-artifacts-s3`](../../crates/artifacts-s3/README.md) for `ArtifactStore` (the files agents hand over; chosen by `artifacts.store`,
[ADR 0032](../../../docs/decisions/0032-files-from-agents-live-in-an-artifact-store.md)), [`orch-secrets-pg`](../../crates/secrets-pg/README.md) for `SecretStore` (a person's own credentials, sealed in the same Postgres; chosen by `secrets.store`, [ADR 0046](../../../docs/decisions/0046-people-add-their-own-mcp-servers-secrets-in-a-credential-broker.md), and used by [`secrets rewrap`](#the-command-secrets-rewrap) and, when `userToolServers.enabled`, by the service), [`orch-credential-broker`](../../crates/credential-broker/README.md) for `CredentialBroker` (built over the sealed store when `userToolServers.enabled` and the file has `secrets`; [`user_tools.rs`](#what-is-in-it)), the system clock and UUIDv7 ids. It has no logic of its own:
what the service does lives in [`orch-app`](../../crates/app/README.md) and
[`orch-api`](../../crates/api/README.md) and the surface crates
([`orch-surface-agui`](../../crates/surface-agui/README.md), [`orch-surface-mcp`](../../crates/surface-mcp/README.md)). Processes are stateless; the only
persistence is Postgres
([ADR 0001](../../../docs/decisions/0001-rust-state-machine-on-postgres.md)).
The role enum (`Role`) and the supervisor (`Host`) are not ours: they come from
the `adam-host` crate of [adam-rs](https://github.com/vymalo/another-adam-rs),
a git dependency pinned to a full commit sha in `orchestrator/Cargo.toml`
(ADR 0015, decision 4); a PR bumps it. Without the feature `agent-local` it brings two crates into the
dependency tree, `adam-host` and `adam-error`, and nothing else from adam-rs: `cargo tree -p orchestrator -i adam-runtime`
finds nothing.
The configuration file is defined and validated by the pure crate [`orch-config`](../../crates/config/README.md); this
binary reads the file, the environment and the secret files and builds its own `Config` from them
([below](#the-configuration-file)). Configuration is the composition root's input, not a port
([ADR 0034](../../../docs/decisions/0034-one-yaml-configuration-secrets-by-reference.md), decision 5).
Running it, the container image, configuration and shutdown are documented in
[`orchestrator/README.md`](../../README.md); the design is in
[`docs/orchestrator.md`](../../../docs/orchestrator.md).

Readiness flips first, so probes answer 503 for the whole drain |

## Environment

Each is also a flag (`--database-url`, `--listen-addr`, `--surfaces`, and so on; `orchestrator --help`), and a flag wins over its variable.

**Deprecated in this release** ([ADR 0034](../../../docs/decisions/0034-one-yaml-configuration-secrets-by-reference.md)):
each variable below is a key of the [configuration file](#the-configuration-file) now (the key each one became is in
[`docs/api/config.md`](../../../docs/api/config.md#every-key)). It still works, over the file, and logs a warning when it is set; the
next release removes them, except `ORCH_CONFIG_FILE`, `ORCH_ROLE`, `ORCH_INSTANCE_ID`, `RUST_LOG`, `HOSTNAME` and the variables
that hold secrets.

| Variable | Default | |
|---|---|---|
| `ORCH_CONFIG_FILE` | unset | the configuration file (flag `--config`): YAML, `version: 1`, read once at startup ([below](#the-configuration-file)). Unset: the environment alone configures the process, as before, with one warning. Kept for good |
| `DATABASE_URL` | required | Postgres connection string, never logged |
| `AGENTS_FILE` | required, unless `AGENT_REGISTRY_URL` is set | YAML list of `{id, name, aliases?, transport?, cardUrl?, tokenEnv?, agent?, gate?}` ([`agents.example.yaml`](../../agents.example.yaml)); `aliases` are other names of the agent, slugs that are no entry's id and no other entry's alias (`ConfigError::AliasCollision`, 78; `Config.agent_aliases` holds them for the composition root, which gives them to `AgentDirectory::with_aliases`; a tool server's `agents` and a role's `agents` may name one, ADR 0049); `gate` is the entry's verification gate, `{require?, maxAttempts?, verifier?, ci?: {required?, timeoutSecs?}}` with `deny_unknown_fields` (see [The gate](#the-verification-gate)); `transport` is `a2a` (the default when absent; `cardUrl` required) or `local` (`agent` required, names a `LocalAgentKind`; `cardUrl` and `tokenEnv` refused). `local` is refused with `LocalAgentsNotCompiled` (78) unless the build has the Cargo feature `agent-local`; any other `transport` is a startup error |

### The configuration file

One YAML file replaces the variables above ([ADR 0034](../../../docs/decisions/0034-one-yaml-configuration-secrets-by-reference.md);
every key, the variable it replaces and the PR that builds it are in [`docs/api/config.md`](../../../docs/api/config.md); the JSON Schema
is [`docs/api/config.schema.json`](../../../docs/api/config.schema.json), which an editor can validate against). It is read once, at
startup: processes are stateless and restart cheaply, so there is no hot reload (open question 43).

```sh
ORCH_CONFIG_FILE=dev/orchestrator.yaml orchestrator            # or --config dev/orchestrator.yaml
orchestrator --config dev/orchestrator.yaml --print-config     # the merged configuration, secrets as references; exit 0 or 78
```

* **Secrets are references**, `{ env: NAME }` or `{ file: PATH }`, never a value; a plain string where a secret goes is an
  error. The variables and files are read at startup, and a reference that does not resolve is an error naming the key and the
  variable or path. A process that serves no routes (`worker`) is not asked for the secrets of the routes it would not mount.
* **Precedence**: a flag or its variable, then the file, then the default. Each variable that is set is read with its own
  parser first (`ORCH_STEPS_RECORD_IO=yes` is `true`), laid over the file, and logged once at startup: a `warn` naming the variable
  and the key (`ORCH_TITLE_MODEL overrides tasks.title.model of the configuration file`), never the value. A secret variable counts
  as a reference to itself, so a file that names `{ env: DATABASE_URL }` is not overridden by `DATABASE_URL`. `ORCH_ROLE` and
  `ORCH_INSTANCE_ID` are process overrides (one file serves a control plane and its workers): they win over `server.role` and
  `server.instanceId` and log at `info`, as do `RUST_LOG` and `HOSTNAME`, which have no key.
* **Three passes, then the rules the binary has always had** ([`orch-config`](../../crates/config/README.md#the-three-passes)):
  syntax (reported alone, by line and column); the variables over the tree; the shape against the JSON Schema (every violation,
  with reserved keys named by the PR and ADR that bring them); the rules between keys and the secrets. The valid file is then
  handed to [`Config::load`](src/config.rs), the same rules the variables go through (a gate against the agents, a surface this build
  compiled in, the agents file, the MCP tokens), so the file and the variables cannot disagree on what is valid. Any error is
  exit **78**, listed on stderr one per line, each naming a key path (a variable that does not parse names the variable) and
  **never a value**: a message of a library or of today's parsers that quotes the value it refused is scrubbed.
* **`--print-config`** prints the configuration this process would run with, the defaults filled in, and opens no connection (it
  reads the agents file and the secrets' variables, as a start does). The notes about variables go to stderr. With no file it
  prints what the environment alone says.
* `agents.file` and `mcp.tokensFile` (and a `{ file }` secret) are relative to the directory of the configuration file, also when a
  legacy variable gave them. The agents file and the MCP tokens file keep their formats.
* A build without a Cargo feature refuses the keys that need it, naming the feature (`server.surfaces` naming a surface that is not
  compiled in, `agents.registry` without `registry-platform`, `agents.localConcurrency` without `agent-local`, `artifacts.store`
  naming `fs` without `artifacts-fs` or `s3` without `artifacts-s3`, `secrets.store` naming `pg` without `secrets-pg`).
* **`artifacts`** ([ADR 0032](../../../docs/decisions/0032-files-from-agents-live-in-an-artifact-store.md)) has no variable: it is a key of
  the file only. Without the section the store is `NoArtifacts` and a file is refused with "no artifact store configured"; the
  environment alone (no file) never has one. `artifacts.fs.root` is relative to the directory of the file; `accessKeyId` and
  `secretAccessKey` of `artifacts.s3` are secret references like every other. **Uploads** ([ADR 0058](../../../docs/decisions/0058-large-files-go-up-through-a-presigned-url-the-orchestrator-gives-the-agent.md),
  [`uploads-v1.md`](../../../docs/api/uploads-v1.md)): `artifacts.s3.publicEndpoint` makes the S3 store sign for that host (it never calls it) and
  `artifacts.upload { maxBytes, ttlSecs }` turns the extension on; the file's rules make it need an S3 store with the public endpoint,
  `threadTools.url` and `secret` and the `thread-tools` surface (exit 78 naming `artifacts.upload` otherwise). `Config::app_config()` gives the
  application the limits **with the thread-tools keys** (`AppConfig.uploads`, a build without the `surface-thread-tools` feature cannot offer
  them), so every role signs and reads the same ids, and `boot.rs` adds `UploadTools` (`request_upload`) to the thread-tools endpoint when it is
  configured. `ConfiguredArtifacts` forwards the optional calls of the port (`can_presign`, `presign_put`, `presign_get`, `head`, `read_prefix`) to the store behind
  it; a default there would hide the S3 store's. **Downloads** ([ADR 0058](../../../docs/decisions/0058-large-files-go-up-through-a-presigned-url-the-orchestrator-gives-the-agent.md) A1): `artifacts.s3.downloads: redirect` (default `stream`, opt-in because the web's policy does not list the files host) and `artifacts.s3.presignTtlSecs` (30 to 3600, 300) reach the application as `AppConfig.downloads` (`ArtifactSettings.downloads`, an `orch_app::DownloadMode` already checked by the file's loader); `redirect` without `publicEndpoint` is exit 78 naming `artifacts.s3.downloads`, and so is a lifetime the application cannot sign (the file's range and `DownloadMode::redirect` agree today; if they did not, the start would refuse, never stream what it was told to redirect). A store that cannot presign streams whatever is set. A control plane that starts with `redirect` logs **one warning** (`ArtifactSettings::warn_about_redirect`): the web's `connect-src` and `img-src` must list the files host (A3, not built), and the files host must add `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and CORS (step 6c), or files break in the web or are served unsafely.
* **`toolServers`** ([ADR 0024](../../../docs/decisions/0024-mcp-tools-attached-per-conversation.md)) has no variable: it is a key of
  the file only, the MCP servers a person may attach to a conversation. What reaches the application (`Config.tool_servers`,
  `AppConfig.tool_servers`) is the public part of each server (id, name, description, icon, the `tools` allow-list, the `agents` it
  is for, the timeout); **the URL and the credentials are in `Config.tool_endpoints` only**, one `orch_ports::ToolServerEndpoint`
  per server (id, URL, timeout, the bearer and the header values resolved, as `ToolSecret`s), which the relay (feature `tool-relay`) reads and nothing else does, and which appear in no `Debug` (the configuration's lists the ids), event, answer or log line. A mistake is exit 78 naming the key, never a value; an `agents` id that is not an
  agent of the agents file is one too (checked only when the file's own list is the whole list, that is, with no platform registry);
  a server that has a credential and a plain `http://` URL logs a warning naming the server.
* The compose stack is configured this way:* The compose stack is configured this way: [`dev/orchestrator.yaml`](../../../dev/orchestrator.yaml) (and
  [`dev/orchestrator.live.yaml`](../../../dev/orchestrator.live.yaml) for `compose.live.yaml`). The `local-agent` profile stays on
  variables, which keeps the old path covered by a stack that runs.

### Authentication

`auth.mode` ([ADR 0033](../../../docs/decisions/0033-the-orchestrator-is-an-oauth2-resource-server.md), keys in
[`docs/api/config.md`](../../../docs/api/config.md#authentication)) has no variable: `proxy_header` (the default, nothing changes), `jwt`,
or `jwt_or_proxy_header`. `src/auth.rs` builds the one `ConfiguredAuth` of the binary's `PortSet` (static dispatch over
`RefuseAll`, the header authenticator, the JWT authenticator and `ByCredential` of both); the log says which at startup, and warns
that the header is trusted when the mode reads it. The configuration refuses, before anything connects: `auth.jwt` missing
(or present with `proxy_header`), `auth.devUser` with another mode, `proxy_header` when `server.environment` is `production`, an
issuer that is not an `http(s)` URL without credentials, query or fragment, no audience, and a mode whose feature is not compiled in. In
`jwt` mode `/readyz` is 503 until the issuer's keys have been fetched (the probe is what fetches them), and the first fetch that
fails is not repeated for 5 seconds.

`auth.dpop` and `auth.browser` ([ADR 0054](../../../docs/decisions/0054-the-web-holds-its-own-tokens-dpop-bound-in-indexeddb.md)) are read into `AuthSettings`: `dpop` becomes the `DpopConfig` of the JWT authenticator (`src/auth.rs`, the public origins and the age and skew of a proof; `ConfiguredAuth` forwards `accepts_dpop()`), and `browser` with the issuer of `auth.jwt` becomes the `BrowserAuth` of `orch_api::ApiConfig` (`src/boot.rs`), which is what `GET /api/public/auth` says. The configuration refuses a `dpop` or `browser` without a mode that reads tokens, a `browser` without `dpop`, origins that are not origins, and, in production, an `http://` origin that is not `localhost`. The replay cache of proofs is in the memory of the process: a split deployment accepts a replayed proof once per process within its window.

### The verification gate

[ADR 0018](../../../docs/decisions/0018-verification-gate-and-rework-loop.md). Three layers (sources can only be added, attempts set anywhere
within the cap): the deployment (`ORCH_GATE`, `ORCH_MAX_ATTEMPTS`, `ORCH_MAX_ATTEMPTS_CAP`, `ORCH_VERIFIER`, `ORCH_VERIFIER_TIMEOUT_SECS`), an agent's
`gate:` in `AGENTS_FILE`, and the run that creates a thread (`forwardedProps["vymalo.gate"]`, see
[`docs/api/agui.md`](../../../docs/api/agui.md#verification-the-gate)). The result is copied into the thread's job when
it is created, so a change of configuration never reaches a running job.

```yaml
- id: coder
  name: Coder
  cardUrl: https://coder.example.com/.well-known/agent-card.json
  gate:
    require: [agent-checks]   # the agent's own `checks` artifact must pass, or it is sent back
    maxAttempts: 2            # 1..=ORCH_MAX_ATTEMPTS_CAP
- id: builder
  name: Builder
  cardUrl: https://builder.example.com/.well-known/agent-card.json
  gate:
    require: [verifier]       # another agent reviews the pushed commit; its `verdict` artifact decides
    verifier: reviewer        # a configured agent (below), never this one
- id: reviewer
  name: Reviewer
  cardUrl: https://reviewer.example.com/.well-known/agent-card.json
  tokenEnv: REVIEWER_A2A_TOKEN   # its own credentials: it never receives the worker's
```

Startup validates all of it and exits **78** with a message naming the variable or the agent: an unknown source; a
`maxAttempts` outside `1..=cap`; an entry whose `require` leaves out a source the deployment requires; a `verifier`
that is not another configured agent; a gate that requires `verifier` with no verifier configured; an agent whose own
gate requires the verifier and that is the verifier itself (its entry must leave `verifier` out of its `require`, the one
removal a layer may make); an unknown member of `gate`. `ci` is honoured since slice 6 (the inbox and timers, slice 5,
and the CI webhook write and apply its reports): a deployment or an entry may require it and set `ci: {required, timeoutSecs}`; a run may add `ci` to `require`
but not set the `ci` settings. **A gate that requires `ci` names the checks that count** (`ci.required`, `ORCH_CI_REQUIRED` for the deployment): the process
exits 78 for a deployment or an entry that requires `ci` without a name, and a run that adds `ci` on a policy with none is a 400.
A process that serves routes and mounts neither `webhook-generic` nor `webhook-github` refuses `ci` in every layer (78 at
startup, 400 for a run) with "no CI webhook surface is mounted (ORCH_SURFACES)"; a `worker` serves no routes and cannot tell, so it
honours what the control plane decides. A source this build cannot honour would be refused in every layer, naming the slice
that enables it (none is left). A run that asks for the same is a 400.

**The verifier** (slice 10): when the worker completes under a gate that requires it, the dispatcher asks the verifier agent
over A2A, in a conversation of its own (the request names no context and the verifier starts one, ADR 0055; it used to be `<thread>-verify-<attempt>-<verification>`), to review the commit the worker pushed, and
its `verdict` artifact `{passed, findings[]}` decides like any other source: findings send the worker back (quoted as
untrusted data), a pass counts toward done. No verdict is a failed check. A verifier that cannot be used (its task fails, it
cannot be reached, it does not answer within `ORCH_VERIFIER_TIMEOUT_SECS`) leaves the thread waiting for the user, `blocked`,
without spending an attempt. A thread may require the verifier in its run but not choose which agent it is.

### Sharing

A thread can be shared by a revocable link ([ADR 0040](../../../docs/decisions/0040-thread-sharing-by-revocable-link.md)). The configuration file's `sharing` section ([`docs/api/config.md`](../../../docs/api/config.md#sharing)) is the only way to turn it on: there is no environment variable. `mode` is `disabled` (the default: no key is read, no route serves a link, the share routes answer that sharing is off), `internal` or `public`; `secret` (and `previousSecret`, for a rotation) are references to secrets, required unless `disabled`, and the file is refused (exit 78, naming the key) when the secret is the thread tools' secret or a public option or a rate limit is set without `mode: public` or is out of range. `src/config/file.rs` (`sharing_of`) turns the section into `orch_app::SharingSettings` for the application and `orch_api::PublicLimits` for the public routes, and `src/boot.rs` passes them with `ApiConfig::check`, which refuses to start with `public` and no limiter. The roles' table in [`docs/api/config.md`](../../../docs/api/config.md#roles-and-permissions) lists `thread.share` (`user` and `admin`). No secret value reaches a log, an error or `--print-config`.

### Logs and metrics

Every log line carries the process's `role` and `instance` (the lease owner), so lines of several
replicas can be told apart in a collector. In JSON they are the first two keys of the object
(`{"role":"worker","instance":"w1","timestamp":...}`); in text the line starts
`role=worker instance=w1 `. They are added by the event formatter (`src/logging.rs`), not by a
span, so the dispatcher's spawned tasks have them too. The configuration is read before logging
starts: a line about an invalid configuration has neither (there is no role yet). While a
dispatcher processes an outbox row, its lines also sit in an `outbox` span (`id`, `thread`,
`kind`, `attempt`; JSON keys `span` and `spans`).

Every role serves `GET /metrics` on `LISTEN_ADDR` without an identity: the outbox queue as
Prometheus text, for dashboards and for scaling the workers (see
[`orch-api`](../../crates/api/README.md#get-metrics) for the samples, and
[`docs/orchestrator.md`](../../../docs/orchestrator.md#observability-and-scaling) for the KEDA
recipe). The edge proxy of the compose stack does not route it.

### Roles

`ORCH_ROLE` is `adam_host::Role`, a closed enum owned by adam-rs, so the names are the same for every
host (adam-coder reads its own `ROLE`). Every role runs the migrations, needs `DATABASE_URL` and
`AGENTS_FILE`, and binds `LISTEN_ADDR`.

| Role | Starts | Serves on `LISTEN_ADDR` | Ready when |
|---|---|---|---|
| `all` (default) | HTTP server, dispatcher, inbox worker, purge sweep and usage retention sweep, as before the role existed | health, resource API, surfaces | the database is migrated and answers |
| `control-plane` | HTTP server; **no dispatcher, no inbox worker, no purge sweep and no usage retention sweep**, so nothing is delivered to an agent and no timer fires from this process (a report received here is stored, and applied by a worker) | health, resource API, surfaces | the database is migrated and answers |
| `worker` | dispatcher, inbox worker, purge sweep, usage retention sweep, and a router with only `/healthz` and `/readyz` | health only: every other path is 404, with or without an identity | the database answers and the dispatcher has started |

The two halves share nothing but Postgres (outbox, thread version compare-and-swap, `LISTEN/NOTIFY`;
[ADR 0015](../../../docs/decisions/0015-control-plane-and-workers-on-adam-rs.md)), so a control plane
and its workers may be any number of processes on any machines. A thread created through a control
plane stays `queued` until some worker runs; a worker that dies mid-task hands it over through the
outbox lease, as before. On shutdown the server drains before the dispatcher stops; a worker's probe
router outlives its dispatcher, so a draining worker answers 503, not connection refused.

The authoritative table, with the meaning of each variable, is in
[`orchestrator/README.md`](../../README.md#configuration). Keep the two in step.

noted in `src/main.rs`.

## The command `artifacts migrate`

```text
orchestrator artifacts migrate --from fs --to s3 --fs-root <dir> [--dry-run] [--allow-empty] [--config <file>]
```

The binary's first command ([ADR 0058](../../../docs/decisions/0058-large-files-go-up-through-a-presigned-url-the-orchestrator-gives-the-agent.md) A5.4). With no command the process is the service, as it always was; every flag and variable above is unchanged (`--help` is not: it gains a `Commands:` section that names `artifacts`).
It copies the files of the **directory store** into the **S3 bucket** the configuration names, so that a deployment that switches `artifacts.store` from `fs` to `s3` does not lose the files of earlier threads (they would read as 404). The chart runs it as a Job on request
([`deploy/chart/README.md`](../../../deploy/chart/README.md#moving-the-files-of-the-directory-store-to-the-bucket-adr-0058-a54)); it can be run by hand.

| Flag | |
|---|---|
| `--from fs`, `--to s3` | both required; **the only values** (anything else is a usage error: clap's exit 2, with the possible values) |
| `--fs-root <dir>` | required: the directory of the directory store, what `artifacts.fs.root` used to be. **Opened read-only**: it must exist and be readable; nothing is created in it and no probe file is written, so a volume mounted read-only works |
| `--dry-run` | read, vet and ask the bucket; write nothing; the report says what would be put (`wouldUpload`, `replaced`) |
| `--allow-empty` | accept a directory that holds **no file of a directory store**: exit 0 and `complete: true` with `empty: true`. Without it that is exit 66: a claim that is not the store's, or is mounted at the wrong path, looks exactly like an empty store, and "nothing to do" would be a success nobody checked. It hides neither a failure nor a link |
| `--config <file>` | the configuration file; the variable `ORCH_CONFIG_FILE` too. They may come before or after the command. `--log-format` (`LOG_FORMAT`, else the file's `log.format`) is the other shared flag (both are the `global` arguments of the struct). Any other flag of the service given on the command line (`--listen-addr`, `--role`, `--print-config`, ...) is a usage error naming it, not ignored; a *variable* of the environment is not a mistake (a Job's environment is the orchestrator's) and means nothing here but `ORCH_CONFIG_FILE`, `LOG_FORMAT` and `RUST_LOG` |

**The configuration.** The file must say `artifacts.store: s3`; its syntax and shape are checked whole, then **only** the rules of the `artifacts` section and the two credentials of the store are checked and read. The database URL, the agents file, the thread-tools key, the model keys and every
other section are neither checked nor read, and **Postgres is never opened**: a Job that only reads a volume and writes a bucket is not given them. (The service's `Loaded::load` resolves every secret of the file; this command uses `Config::validate_artifacts` of
[`orch-config`](../../crates/config/README.md) instead.) The store is built as the service builds it (`ConfiguredArtifacts::build`: the same bucket, region, endpoint, prefix, credentials and timeout), without a public endpoint: nothing is presigned. A file with no `artifacts` section,
a store other than `s3`, or a credential that does not resolve is exit 78 naming the key.

**What it does**, per file of `<root>/threads/<thread uuid>/<sha256>` (with its `.meta.json`), in key order, one at a time: the directory store reads it (meta against key, size against meta); the migration holds the bytes (one file in memory, at most `artifacts.maxFileBytes`, the ingest's own limit: a file
over it is `tooLarge` and not read), runs `ArtifactMeta::check` (the bytes hash to the key, the type and name are text a header can carry); a file that fails is `failed` and **never uploaded**. Then it asks the bucket (`head`): present with the same size and the key's hash (the checksum the server says, else the
object is read back and hashed) is `skipped`; absent, or of another size or other bytes (`replaced`), it is put through `ArtifactStore::put` under **the same key**, with the meta as the object's metadata exactly as a plain put writes it, and asked again, **by content**: the bucket's checksum when it says one, else the object is read back and hashed as it streams (one read per uploaded file), so a bucket that kept other bytes of the same length is a failure and not an upload. It continues past a file that failed and reports them all. After five files in a row on which the bucket failed it stops
(`notAttempted`): an unreachable bucket would otherwise cost every remaining file its retries. **It deletes nothing, from the directory or from the bucket.** What the directory holds that is not a file of the store (a temporary file of a crashed write, bytes with no meta, a meta with no bytes, a link, a name the
store never writes, a name of a thread that is not a directory) is `ignored`: counted and named, never a failure. **A link is not**: the directory store follows one and the migration does not, so a link where a file or a thread's directory belongs (and a directory or a special file where a file belongs) is `unreadable`, named by path and reason, and the run is not complete (exit 65). A listing whose `threads` directory is a link is the same.

**The report** is stdout: one line of JSON (the logs are on stderr, in the configured format).

```json
{"dryRun":false,"complete":true,"empty":false,"files":3,"uploaded":2,"replaced":0,"skipped":1,"wouldUpload":0,"failed":0,"notAttempted":0,"unreadable":0,"ignored":1,
 "bytesUploaded":30,"bytesSkipped":11,"bytesWouldUpload":0,"failures":[],"unreadableEntries":[],"ignoredEntries":[{"path":"threads/<uuid>/.tmp-...","why":"a temporary file of a write that did not finish"}]}
```

`files` is `uploaded + skipped + wouldUpload + failed + notAttempted`. Each entry of `failures` is `{"key","kind","reason"}` with `kind` one of `unreadable`, `corrupt`, `invalid`, `tooLarge`, `target`; a reason names no path, URL or credential. Each entry of `unreadableEntries` is `{"path","reason"}` (a path under the root, such as `threads/<uuid>`; not a file, so not in `files`). At most 100 `ignoredEntries` and `unreadableEntries` are listed (all are counted and logged). `empty` is true when the directory holds no file. `complete` is true when nothing failed, nothing was left untried, no entry was unreadable **and there was at least one file** (or `--allow-empty` said that none is fine).

| Exit | Meaning |
|---|---|
| `0` | every file is in the bucket, proven by its content (on a dry run: nothing failed; `wouldUpload` says what a real run would do), and there was at least one file (or `--allow-empty`) |
| `2` | a usage error (clap): a missing flag, a value other than `fs` or `s3`, a flag of the service, `--print-config` |
| `65` | a file is damaged or cannot be migrated (`unreadable`, `corrupt`, `invalid`, `tooLarge`), or an entry is a link (or a directory or special file where a file belongs) that the migration does not follow, whatever else failed: the report names it; the others were migrated |
| `66` | `--fs-root` is missing, is not a directory or cannot be read, **or holds no file of a directory store** (`"empty":true`, `"complete":false`, and a line on stderr: `no file of a directory store under <root>`) unless `--allow-empty`. The same code: both are the wrong claim, or the wrong path |
| `69` | the bucket failed on a file and on nothing else (`target`: unreachable, refused credentials, not holding the file after a put): running it again resumes |
| `78` | the configuration (no file, a store that is not `s3`, an unresolved credential), or a build without the features `artifacts-fs` and `artifacts-s3` |

Run it twice and the second run changes nothing. `kill` it half way and run it again: it skips what is there.

## The command `secrets rewrap`

```text
orchestrator secrets rewrap [--config <file>]
```

The binary's second command ([ADR 0046](../../../docs/decisions/0046-people-add-their-own-mcp-servers-secrets-in-a-credential-broker.md), slice 3). It re-seals the secrets that people keep for their own MCP servers under the **current** key of `secrets.pg`, for a key rotation:
add a key to `secrets.pg.keys`, make it `secrets.pg.current`, restart every replica **and wait until none runs the old configuration** (a pod still on the old `current` seals under the old key after the run), run this, and when it exits `0` (and a second run finds every secret current) remove the old key from the file. **Never change the bytes behind a key id** (overwrite the property or file a key is read from, or remove a key and later add a different one under its name): add a new id. A key id is all a row says of its key, so the old rows no longer open. It is the one place the running binary uses
[`orch-secrets-pg`](../../crates/secrets-pg/README.md) today; the service reads and checks the `secrets` section (every role does) and uses it only when `userToolServers.enabled` is true and the process serves routes (`all`, `control-plane`: the sealed store and the broker are then built at startup; with it off, or in a `worker`, nothing is opened or migrated). No flag of its own: it is idempotent and keeps what it re-seals. The chart does not run it
([`deploy/chart/README.md`](../../../deploy/chart/README.md#the-key-of-the-stored-secrets-adr-0046-slice-3) says how to run it once, as a one-off command).

**The configuration.** The file must have a `secrets` section; its syntax and shape are checked whole, then **only** `database.url`, the rules of the section and its keys are checked and read ([`Config::validate_user_secrets`](../../crates/config/README.md)). The agents file, the thread-tools key, the model keys and every other section are neither checked nor read: the command is
not given them. `--config` (or `ORCH_CONFIG_FILE`) and `--log-format` are the shared flags and may come before or after the command; any other flag of the service on the command line is a usage error naming it, as for `artifacts migrate`.

**What it does.** It connects to the database (a pool of two connections, ten seconds to get one), applies the crate's migrations (so it can run before the service has ever started), and re-seals, one secret at a time, under that secret's lock: a secret that is not under the current key is opened with the key it names and sealed again **at the same version**, with a new nonce and
the current key (not through `rotate`: a refresh of an OAuth token that has claimed the grant would find a new version and lose the refresh token the authorization server rotated to). A secret that was written or deleted while the run was under way is left alone and counted. A secret sealed under a key the file does not list, or one that does not open, is counted as failed, named, and left as it was.
**A secret already under the current key is opened too** (nothing is written for it), and counted as failed if it does not open: the id of a key is not its bytes, so if the bytes behind the current id are not the ones that sealed the row (the rule above, broken), the run says so instead of reporting the row as current.
It writes nothing for a secret it counts as anything but rewrapped. A secret whose lock is held for more than two seconds (a writer that is wedged, a repair left open) ends the run with `69`: the secrets before it are done, and the run can be repeated once the lock is let go.

**The report** is stdout: one line of JSON (the logs are on stderr, in the configured format). It names a failure by the server (`u-…`) and the key the secret is sealed under, never the person, and no key or secret appears in either stream.

```json
{"complete":true,"currentKey":"k2","rewrapped":4,"alreadyCurrent":0,"changed":0,"failed":0,"failures":[]}
```

`failures` lists at most 100 (`{"server","kid","kind"}`, `kind` `keyUnknown` or `corrupt`); `failed` counts all. `complete` is true when nothing failed and nothing changed under the run.

| Exit | Meaning |
|---|---|
| `0` | every secret is under the current key and opens with it: none failed and none changed while the run was under way (nothing to do is also `0`) |
| `2` | a usage error (clap): an unknown flag, `secrets` alone, a flag of the service, `--print-config` |
| `65` | at least one secret could not be re-sealed or does not open: sealed under a key the file does not list (`keyUnknown`: put that key back and run again) or it does not open with the key it names, the current one included (`corrupt`: investigate; if every secret is `corrupt`, the bytes behind a key id changed). The others were re-sealed |
| `69` | the database could not be reached or failed, or a secret's lock was held for more than two seconds: run it again (the secrets done are counted as current) |
| `70` | the history of the crate's migrations does not match this build, or another internal error |
| `75` | nothing failed, but a secret was written or deleted while the run was under way, and was left alone. A writer on a replica that still runs the old configuration seals under the old key, so remove no key until a run exits `0` |
| `78` | the configuration (no file, no `secrets` section, a key or the database URL that does not resolve), or a build without the feature `secrets-pg` |

## The command `usage backfill`

```text
orchestrator usage backfill [--page <N>] [--config <file>]
```

The binary's third command ([ADR 0065](../../../docs/decisions/0065-a-usage-ledger-per-person.md)). It folds into the **usage ledger of the people** the usage events that the log holds and the ledger has not been through: the threads that existed before migration `0023`, and those a build without the ledger wrote to during a rollout. Run it **once after the rollout** that brings the ledger (`kubectl exec deploy/<orchestrator> -- /orchestrator usage backfill`, or a Job); a thread that someone writes to is caught up by its next commit anyway, so the command is for the threads no one writes to any more.

**The configuration.** `--config` (or `ORCH_CONFIG_FILE`) and `--log-format` are the shared flags and may come before or after the command. The file's syntax and shape are checked whole, then **only** `database.url` is checked and read ([`Config::validate_database`](../../crates/config/README.md)); the agents file, the thread-tools key, the model keys and the secret store's keys are neither checked nor read, and any other flag of the service on the command line is a usage error naming it. `--page <N>` (1 to 10 000, default 100) is how many threads a page goes through.

**What it does.** It connects (a pool of two connections), applies the store's migrations (so it can run before the service has ever started), then asks the store for pages of the threads whose log the ledger has not been through: each thread is one transaction, under the lock of the thread's row (the lock every commit takes), in which the usage events above the thread's `usage_through` are folded in and the watermark moves to the thread's last event. So it **can run while the service does**, and **running it again finds nothing**: the report of a second run has `threads` and `events` at zero. The events a fork copied from its parent are not counted (they were counted in the parent). A usage event that does not decode is left out and logged. The usage of a thread that was erased before the command ran is not in the log any more and is not recovered. The events of a thread are read in pages of 500 and folded into each task's row in memory, and each row that changed is written once, so a thread of 10 000 events on three tasks takes a fraction of a second under its lock, not tens of seconds. **It never waits long for a thread**: a thread whose lock is held for more than 5 seconds (a commit that is slow, or a transaction that is stuck) is left alone, counted as `skipped`, and the run goes on; the commit that holds the lock catches the thread up when it ends, and the next run of the command would. **The first page also cleans up after older builds**: a build that does not know the ledger erases a thread and leaves the `thread_id` of its rows, so the rows whose thread no longer exists are made to name none (`detached`); the usage stays.

**The report** is stdout: one line of JSON (the logs are on stderr, in the configured format). `pages` is how many pages it asked for, `threads` how many threads it went through, `events` how many usage events it folded in, `skipped` how many threads it left alone because their lock was held (then `complete` is `false`), `detached` how many rows it made to name no thread.

```json
{"complete":true,"pages":3,"threads":250,"events":4100,"skipped":0,"detached":0}
```

| Exit | Meaning |
|---|---|
| `0` | the ledger has been through every thread's log (nothing to do is also `0`) |
| `2` | a usage error (clap): an unknown flag, a `--page` outside 1 to 10 000, `usage` alone, a flag of the service, `--print-config` |
| `69` | the database could not be reached or failed: run it again, it resumes where the ledger is |
| `70` | the history of the store's migrations does not match this build, or another internal error |
| `75` | nothing failed, but `skipped` threads were left alone because their lock was held (`complete` is `false`): run it again, it takes them |
| `78` | the configuration (no file, a database URL that does not resolve) |

`POST /api/threads/{id}/messages`, `GET /api/threads/{id}/events`, `GET /api/threads/{id}/stream`),

([ADR 0012](../../../docs/decisions/0012-ag-ui-user-facing-protocol.md)). Those routes answer 404
(`POST /api/threads` answers 405, because its path is also the thread list).

**Migrating an existing deployment.** An `ORCH_SURFACES` (or `--surfaces`) that still lists
`chat-api` fails closed: the process exits 78 (`EX_CONFIG`) before it connects to anything,
with

```text

the resource API (GET /api/threads, GET /api/threads/{id}, GET /api/agents, cancel) is unchanged
```

Nothing is quietly ignored: drop `chat-api` from the list (or unset the variable) and move the
client. Create a thread and send a message with one `POST /agui/agents/{agentId}` (a UUID you
mint as `threadId`), read the log with `GET /agui/threads/{threadId}/connect`
([`docs/api/agui.md`](../../../docs/api/agui.md)). The web app has run on AG-UI only since
2026-09-29.
