# orch-app

The orchestrator application: the thread service (`App`), the durable
outbox `Dispatcher` and the `InboxWorker` that applies timers and stored
reports, written against the ports only.

## Where it sits

The application layer between [`orch-ports`](../ports/README.md) and
[`orch-api`](../api/README.md). `App<P: Ports>` runs
[`orch_core::transition`](../core/README.md) inside an optimistic commit loop
against a `ThreadStore`; `Dispatcher<P>` claims outbox rows and delegates them
to an agent through `AgentClient`; `InboxWorker<P>` claims inbox rows (a timer
that came due, a CI report a surface stored) and applies them to their thread. Because it depends on the traits only
([ADR 0009](../../../docs/decisions/0009-swappable-implementations-at-build-time.md)),
any composition of adapters runs it; state lives in the store, not here
([ADR 0001](../../../docs/decisions/0001-rust-state-machine-on-postgres.md)).
Design: [`docs/orchestrator.md`](../../../docs/orchestrator.md).

## API at a glance

| Item | What |
|---|---|
| `App::new(ports, AgentDirectory, AppConfig) -> Result<App<P>, GateError>` | the thread service; `App<P>` is shared as `Arc<App<P>>`. It refuses a gate the build cannot honour (`GateRules::validate` over `AppConfig.gate` and `target_gates`), so a composition root cannot bypass the rules; the binary exits 78 |
| `App` operations | `list_agents`, `describe_agent(id)` (one configured agent and its live card, `AgentDescription { id, name, card: Option<AgentCardInfo> }`; `None` for an unknown id, a card that cannot be read in time gives `card: None`), `create_thread(user, NewThread)`, `list_threads`, `get_thread`, `export_thread(user, id) -> ThreadExport { thread, binding, events, truncated, exported_at }` (a snapshot of one of the user's threads for sharing: the thread with its full job, the A2A binding and the whole log read in pages through `ThreadStore::list_events`, up to `AppConfig::max_export_events` events and `AppConfig::max_export_bytes` bytes of serialized events, whichever comes first, flagging `truncated` and keeping the head; someone else's thread is `NotFound`; nothing new is asked of the store), `list_events`, `post_message`, `cancel`, `find_thread(user, id)` (mine, free, or someone else's = `NotFound`), `create_thread_as(user, id, NewThread, Inbound)` (a thread id the caller chose; a taken id is `NotFound` for a stranger and `Creation::Exists` for the owner), `submit(user, thread, input, key)` (an already translated `Input` under an idempotency key, text or action validated: an oversized or malformed `Input::UiAction` is `AppError::Invalid` and nothing is written), `apply(thread, input, key, binding, lease)` (feed an `Input`, retrying on version conflicts; the API passes `lease: None`, the dispatcher its claim, and a claim that is no longer current gives `ApplyOutcome::Fenced`, not retried), `apply_finishing(thread, input, key, &Lease, OutboxFinal)` (the same as `apply` under a claim, and the claimed outbox row is finished with the given outcome in the same commit; the dispatcher uses it for `Input::Redeliver`, so a crash between the commit and the row's completion cannot send the message twice; `Duplicate` when the key was applied before), `apply_from_inbox(thread, input, &InboxLease)` (the same for an input the inbox delivered: the key is `inbox:<row id>`, the row is marked `applied` in the same commit, or completed on its own when the input changed nothing or was a repeat, and a claim that is no longer current gives `Fenced`), `receive(source, idempotency_key, InboxPayload) -> Received::{Stored { id }, Duplicate}` (the entry point of the surfaces that take machine input, the webhook of slice 6, `orch-surface-webhook`, which calls it after it has checked the signature: it stores the report and returns; the same pair twice is a duplicate; `AppError::Invalid` for a `source` or key that is empty, oversized or not printable ASCII (both reach logs), the reserved source `timer`, a timer payload, which only the store makes, or a CI report whose repository is not a repository address or whose sha is not a full commit hash. A CI report's correlation is not the sender's to choose: it is always the watch key `ci:<repo-key>@<sha>`, built after the repository is put through `repo_key` and the sha is lower-cased, so a report can only reach a thread that watches that very commit), `record_binding` (same `lease`), `outbox_stats()` (the open outbox rows counted at the clock's now, returned with that now; behind `/metrics`), `event_stream(user, thread, after)` (replay then live, no gaps or duplicates; wakeups make it prompt, a poll makes it correct) |
| `App` lifecycle | `set_ready`, `is_ready`, `set_shutting_down`, `is_shutting_down`, `ports()`, `directory()` |
| `AppConfig` | `card_timeout` (3 s), `stream_poll` (5 s), `max_commit_attempts` (8), `max_export_events` (`DEFAULT_MAX_EXPORT_EVENTS`, 50 000: the most events an export reads), `max_export_bytes` (`DEFAULT_MAX_EXPORT_BYTES`, 32 MiB: the most bytes of serialized events it reads; either bound cuts), `gate` (the deployment's `GatePolicy`, the base a new thread's job starts from; the default requires nothing, which is the behaviour from before the gate existed), `target_gates` (an agent's `gate` key of `AGENTS_FILE`, by agent id) and `gate_rules` (`GateRules`: which sources this build honours and the attempts cap) |
| `GateLayer`, `GateRules`, `Layer`, `GateError`, `SourceName`, `CiLayer`, `pending_reason`, `THREAD_GATE_KEY`, `DEFAULT_MAX_ATTEMPTS_CAP` | the gate's configuration ([ADR 0018](../../../docs/decisions/0018-verification-gate-and-rework-loop.md)), in `gate_config.rs`. A `GateLayer` is `{require?, maxAttempts?, verifier?, ci?}` (`deny_unknown_fields`, camelCase; sources are spelled `ci`, `agent-checks`, `verifier`), read from YAML (`AGENTS_FILE`), JSON (`GateLayer::from_json`, the `forwardedProps["vymalo.gate"]` value) or built from the environment. `GateRules::apply(above, layer, at)` puts a layer on the policy above it and refuses: a source or setting this build cannot honour (every source is honoured since slice 10; `pending_reason` is where a source that is not built yet would say which slice enables it), a `require` that leaves out a source the layer above requires, `maxAttempts` outside `1..=cap`, a `verifier` or `ci` per thread. `GateRules::validate` checks every agent's resolved gate at startup, and that each verifier is another configured agent. `App::resolve_gate(agent, request)` is the deployment, then the agent's entry, then the request (a refused request is `AppError::Invalid`, a 400); `App::gate_request_changes(current, request)` says whether a run's request would change the gate a thread already has (the surface refuses that with a 409). Also `MAX_ATTEMPTS_CAP_CEILING` (100) and `GateRules::check_policy`. Sources: layers add, never remove (except the verifier's own entry, for itself), `ci.required` names add up, attempts anywhere within `1..=cap`; both `agent-checks` and `agent_checks` are read |

`apply` runs `transition` on the thread's snapshot (state and job) and commits both together, writing the job only when it changed. The gate's `Watch` and `Schedule` commands are executed since slice 5: they become `Commit.watches` and `Commit.timers` of the same commit (the store adds a timer's `after` to the commit's time, so the core never reads a clock). `RequestVerification` is executed since slice 10: it becomes an outbox row of kind `verify` (`OutboxPayload::Verify`) in the same commit, and the dispatcher asks the verifier (next row). `submit`, the entry point for a user's request, refuses the machine inputs (`CiReported`, `VerifierReported`, `VerifierFailed`, `TimerFired`) with `AppError::Invalid`, so a user cannot forge a check result. |
| `NewThread`, `Inbound` (`message_id`, `run_id`, `key` a surface records in the log, and `gate`, the layer the request asks for; it applies when the request creates the thread, and `origin`, the `Origin` (`agui` by default, or `mcp`) it writes on the `user_message`), `Creation` (`Created` / `Exists`), `ApplyOutcome` (`Applied` / `Duplicate` / `Fenced`) | request and result types |
| `AgentDirectory`, `AgentEntry` | the static set of agents users can target (from configuration) |
| `Dispatcher::new(app, DispatcherConfig, owner)`, `run(shutdown)` | the durable outbox worker: concurrency, lease and heartbeat, retry with backoff, adaptive polling, cancel retries; every write it makes is fenced with the claim's attempt, so a worker paused past its lease drops its late result instead of writing it. **A thread is a conversation** (ADR 0020): a `delegate` row that finds its thread `done` or `failed` and unsent is applied as `Input::Redeliver` (key `redeliver:<row id>`) and skipped, so a message queued behind the one that ended the job starts the next job (on a `cancelled` thread it is skipped as before); a `cancel` row whose `job` is not the thread's current job is finished without calling the agent. **The verifier path** (`verify` rows, ADR 0018, slice 10; `src/dispatcher/verify.rs`): it sends the core's prompt to the verifier agent in the context `<thread>-verify-<attempt>-<verification>`, records the verifier's task on the row (never on the thread's binding), reads its envelopes without ever applying them as the worker's (`Input::Agent`), and feeds exactly one input: `VerifierReported` from the `verdict` artifact (none, or an unusable one, is a failed verdict that says "no verdict"; applied under the key `verdict:<row>`), or `VerifierFailed` when the verifier cannot be used (its task failed or asked for input, it is unreachable after the delegation's retries, it refused the request, it is no longer configured). A row whose verification is no longer the one in progress (a timeout, a cancel, a message from the user, another source failed the round) is dropped without asking, or, when the verifier is already at work, the verifier is told to stop (`DispatcherConfig::verify_watch`, 5 s, is how often a verification in flight looks: between two envelopes or two polls, never in the middle of a write, so a request that was sent is recorded first and a verdict being committed is finished); a re-claimed row re-attaches to the recorded task (`resubscribe`, else `get_task`; a task that completes on the resubscribed stream with no verdict is read with `get_task` first, since that stream lacks what came before) or finds the message by its id (retried when the lookup itself fails, and the request goes out again only when the lookup says there is no such task), so the verifier is asked at most once when it supports `ListTasks` |
| `InboxWorker::new(app, InboxConfig, owner)`, `run(shutdown)`, `tick()` | the durable inbox worker, run wherever the dispatcher runs (the `worker` and `all` roles). Each pass expires the parked rows older than `parked_ttl`, claims a batch of due rows and applies each: a timer names its thread and becomes `TimerFired`; a CI report is matched to its thread through `watches` by its correlation and becomes `CiReported`, or is parked when nothing watches it yet (and put straight back if the watch appeared meanwhile). A retryable failure puts the row back with a doubling backoff (`backoff_base` 1 s, `backoff_max` 60 s) until `max_attempts` counted claims, a permanent one (no such thread, an unreadable payload) dead-letters it at once; a lost claim drops the late result. A row that was claimed more than `max_attempts` times without ever being finished (its workers died with it: a panic, the OOM killer) is dead-lettered before it is delivered, since no error path saw those claims; claims handed back at shutdown or ended by a park are not counted. An input that changes nothing finishes its row in a commit of its own (the claim and the thread's version are checked), not with a bare completion. A wakeup (`Topic::Inbox`) makes it prompt, `poll_interval` makes it correct. On shutdown it finishes the row in hand and releases its claims. `tick()` is one pass, for tests |
| `InboxConfig` | `lease` (30 s), `poll_interval` (2 s), `batch` (16), `parked_ttl` (86 400 s), `max_attempts` (10), `backoff_base`, `backoff_max` |
| `AppError` | classified via `orch_core::Classify` |

```rust
use std::sync::Arc;
use orch_app::{AgentDirectory, App, AppConfig, Dispatcher, DispatcherConfig, InboxConfig, InboxWorker};
use tokio_util::sync::CancellationToken;

let app = Arc::new(App::new(ports, AgentDirectory::new(entries), AppConfig::default()));
let dispatcher = Dispatcher::new(app.clone(), DispatcherConfig::default(), "replica-1");
let shutdown = CancellationToken::new();
tokio::spawn(dispatcher.run(shutdown.clone()));
let inbox = InboxWorker::new(app.clone(), InboxConfig::default(), "replica-1");
tokio::spawn(inbox.run(shutdown.clone()));
```

## Features and environment

No Cargo features. The crate reads no environment variables; the binary maps
`DISPATCHER_CONCURRENCY`, `OUTBOX_LEASE_SECS` and friends onto
`DispatcherConfig`, and `INBOX_LEASE_SECS`, `INBOX_POLL_SECS`,
`INBOX_PARKED_TTL_SECS` and `INBOX_MAX_ATTEMPTS` onto `InboxConfig` (see
[`orchestrator`](../../bin/orchestrator/README.md)).

## Tests

Offline: they use the in-memory implementations of `orch-ports` (feature
`testkit`). No environment variables.

* `tests/service.rs`: the thread service without a dispatcher (validation,
  isolation between users, streams, idempotency, consumer-chosen thread ids and their collisions, `submit`; `list_agents` reads live cards,
  fails closed and keeps configuration order, so the first agent stays the default; `describe_agent` is one agent with its card, live, `None` card when unreadable; `export_thread` is the thread, its binding and the whole log in order across the store's pages, bounded by `max_export_events` and `max_export_bytes` and flagged when either cuts, and someone else's thread is `NotFound`).
* `tests/gate_config.rs`: `App::new` refusing a gate that could never pass, the layers (`GateRules`): `ci` is refused in every layer with the slice named and the verifier is honoured, a layer adds sources and changes attempts within the cap, cannot remove a required source or choose the verifier per thread, is read strictly, the verifier is another configured agent, startup validation of every agent, and the thread created under deployment, entry and request (a refused request is a 400 and writes nothing).
* `tests/gate.rs`: the gate through the thread service: the job is created with the thread and saved with every change, a failed check reworks (a second delegation with the person's request and the findings), checks with no pushed commit never end the thread `done` (the owner's "Hi" of the first live run: reworked twice, then `failed` with "no pushed commit") and running out of attempts fails the thread, a thread keeps the gate it was created under when another replica is configured differently, `verifying` can be left by a CI report or a cancel, a user cannot submit a CI report, and a crash after a rework followed by a replay of the old task's envelopes (`completed` included) writes nothing.
* `tests/inbox.rs`: the inbox worker on a `FixedClock` the test moves and one `tick` at a time, so nothing waits: a gated completion writes its watch and its timer in its own commit; a timer is not claimed one second early, fires when due, blocks the thread once and marks its row applied; a stale timer is applied and changes nothing; a report that beats its watch is parked, re-armed by the commit that adds the watch and applied, and its redelivery is a duplicate; parked rows expire after the time-to-live and a late watch does not revive them; a row a dead worker held is applied once by another after the lease lapses and the late worker is fenced; a retryable failure backs off, doubles and dies after `max_attempts`; a report for a thread that does not exist is dead-lettered at once; `receive` refuses what a surface may not send (a timer, the reserved source, control characters and non-ASCII in the source or key, an address or sha that cannot match a watch); a report spelled `https://github.com/O/R.git` with an upper-case sha reaches the watch of `github.com/o/r`; a row whose workers kept dying (lapsed leases, more claims than `max_attempts`) is dead-lettered without being delivered, one claimed exactly as often as allowed still is, and claims handed back at shutdown are not counted; an input that changes nothing finishes its row through a commit that checks the version (a store fault on that commit retries the row); a watch that lands between the worker's lookup and its park is not missed (a store that runs a commit in that window); a running worker applies a received report on a wakeup and stops on shutdown; shutdown releases the claims.
* `tests/verifier.rs`: the verifier path against a scripted verifier (`ScriptedAgent::set_verifier`), one case per way a `verify` row ends: the request becomes a row with its payload and its deadline, a pass finishes the job and is never the worker's update (the verifier's own context, the row as the message id, its task on the row and not the binding), findings on the last attempt fail it, no verdict and a garbled one fail the check, a failed or asking verifier, an unreachable one (retried, then held, no transport text in the chat), a refused request (not retried) and one no longer configured hold the thread, an abandoned verification is dropped without asking, a hanging verifier is told to stop when the deadline holds the thread, a worker that lost its claim writes nothing, a reclaimed row follows the task and a request that reached the verifier before a crash is found and not sent again.
* `tests/dispatcher.rs`: the dispatcher against the scripted agent, including a late result after another claimer (or the same owner name) re-claimed the row, with a heartbeat that never fires so only the fence can stop the old worker. A Stop right after a follow-up (or a rework) never cancels the task that ended; a new job opens a new task even when the last one still waited for input; a redelivery whose worker died at its commit is redone once and the message is sent once. Each claimed row is processed inside an `outbox` span (`id`, `thread`, `kind`, `attempt`), so every log line of that work carries them.
* `tests/a2ui.rs`: a surface is recorded before the question it accompanies, an action answers it and reaches the agent as an action on the same task, a replayed action is written once, an oversized action writes nothing, the action row is a delegation with its own payload.
* `tests/restart.rs`: two app instances over one shared in-memory "database",
  the first killed mid-stream.

Against real HTTP and Postgres, see [`orch-e2e`](../e2e/README.md).
