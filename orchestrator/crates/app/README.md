# orch-app

The orchestrator application: the thread service (`App`), the durable
outbox `Dispatcher` and the `InboxWorker` that applies timers and stored
reports, written against the ports only.

## Where it sits

The application layer between [`orch-ports`](../ports/README.md) and
[`orch-api`](../api/README.md). `App<P: Ports>` runs
[`orch_core::transition`](../core/README.md) inside an optimistic commit loop
against a `ThreadStore`; `Dispatcher<P>` claims outbox rows and delegates them
to an agent through `AgentClient`; `InboxWorker<P>` claims inbox rows (a timer
that came due, a CI report a surface stored) and applies them to their thread. Because it depends on the traits only
([ADR 0009](../../../docs/decisions/0009-swappable-implementations-at-build-time.md)),
any composition of adapters runs it; state lives in the store, not here
([ADR 0001](../../../docs/decisions/0001-rust-state-machine-on-postgres.md)).
Design: [`docs/orchestrator.md`](../../../docs/orchestrator.md).

| `Dispatcher::new(app, DispatcherConfig, owner)`, `run(shutdown)` | the durable outbox worker: concurrency, lease and heartbeat, retry with backoff, adaptive polling, cancel retries; every write it makes is fenced with the claim's attempt, so a worker paused past its lease drops its late result instead of writing it. **A thread is a conversation** (ADR 0020): a `delegate` row that finds its thread `done` or `failed` and unsent is applied as `Input::Redeliver` (key `redeliver:<row id>`) and skipped, so a message queued behind the one that ended the job starts the next job (on a `cancelled` thread it is skipped as before); a `cancel` row whose `job` is not the thread's current job is finished without calling the agent. **The verifier path** (`verify` rows, ADR 0018, slice 10; `src/dispatcher/verify.rs`): it sends the core's prompt to the verifier agent in the context `<thread>-verify-<attempt>-<verification>`, records the verifier's task on the row (never on the thread's binding), reads its envelopes without ever applying them as the worker's (`Input::Agent`), and feeds exactly one input: `VerifierReported` from the `verdict` artifact (none, or an unusable one, is a failed verdict that says "no verdict"; applied under the key `verdict:<row>`), or `VerifierFailed` when the verifier cannot be used (its task failed or asked for input, it is unreachable after the delegation's retries, it refused the request, it is no longer configured). A row whose verification is no longer the one in progress (a timeout, a cancel, a message from the user, another source failed the round) is dropped without asking, or, when the verifier is already at work, the verifier is told to stop (`DispatcherConfig::verify_watch`, 5 s, is how often a verification in flight looks: between two envelopes or two polls, never in the middle of a write, so a request that was sent is recorded first and a verdict being committed is finished); a re-claimed row re-attaches to the recorded task (`resubscribe`, else `get_task`; a task that completes on the resubscribed stream with no verdict is read with `get_task` first, since that stream lacks what came before) or finds the message by its id (retried when the lookup itself fails, and the request goes out again only when the lookup says there is no such task), so the verifier is asked at most once when it supports `ListTasks`. **The description path** (`description` rows, `src/dispatcher/description.rs`, [ADR 0035](../../../docs/decisions/0035-utility-model-tasks.md)): the same pattern as the title's, ending in exactly one input under the key `description:<row id>`: `Described` (the model's words, cleaned by `clean_description`) or `DescriptionDeclined` (the task switched off since, too few new messages, nothing to describe yet, the model unreachable or refusing, or a wrong script twice). It reads the **head** (16 events) and the **tail** (512) of the log, never all of it, and counts `messages_since_description`: **below the task's `min_new_messages` it declines and no model is asked**; otherwise it asks with the previous description, applies the language rule (asking once more in the same row for a wrong script) and never fails the thread; a row whose thread has a person's description ends `skipped`. **Both utility workers ask through one `ask_model`** (`src/dispatcher/utility.rs`): up to 3 tries on a transient failure with the dispatcher's backoff, each bounded by the task's `timeout` (its endpoint's), a refusal for good and an endpoint the model does not hold given up at once. **The title path** (`title` rows, `src/dispatcher/title.rs`; the task says the endpoint, model, guidance, tokens and language rule): the row asks the model for a short title, and whatever happens it ends in the commit of exactly one input, under the key `title:<row id>` and finishing the row in the same commit: `Titled` (the model's words, cleaned to one line by `clean_title`) or `TitleDeclined` (titles off, the model unreachable or refusing, or `NONE`). It reads the head of the log when the row is worked (128 events, fenced as data by `title_prompt`), never fails the thread and holds nothing back; a row whose thread has the person's title, or that finished meanwhile, is dropped or applied without moving the thread; a transient failure (a timeout of `title_timeout`, a 5xx, a rate limit with its `Retry-After`) is tried up to 3 times with the dispatcher's backoff and then declined, a refusal for good is declined at once; a title in a script none of the person's messages uses (`check_title_language`: the Chinese title of an English thread) is declined and the model is **asked once more in the same row** (`title_retry_prompt`: what was wrong, the language named last again), and the row is declined if that is wrong too **The agent is read from the registry** (`App::resolve_agent`, ADR 0022) for every `delegate` and `cancel` row, so an agent the platform added is served without a restart: when the registry answers without the agent the row is dead-lettered ("agent '<id>' is no longer listed"), and when it cannot answer the row is retried with the backoff curve and never dead-lettered for it (the registry being down is not the agent being gone; the thread waits). The verifier is a static agent and is looked up in the `AgentDirectory` The **first task of a fork** (the thread was forked and its binding has no task yet, a text message) is sent with `SendRequest.history`: the dispatcher reads the fork's own events `1..=forked_at` in pages and builds `orch_core::fork_history`, so a retry sends the same words and nothing of it is stored in the outbox ([ADR 0029](../../../docs/decisions/0029-forking-a-thread-copies-its-log.md)); the verifier's request has none. |
| `InboxWorker::new(app, InboxConfig, owner)`, `run(shutdown)`, `tick()` | the durable inbox worker, run wherever the dispatcher runs (the `worker` and `all` roles).
```rust
use std::sync::Arc;
use orch_app::{AgentDirectory, App, AppConfig, Dispatcher, DispatcherConfig, InboxConfig, InboxWorker};
use tokio_util::sync::CancellationToken;

let app = Arc::new(App::new(ports, AgentDirectory::new(entries), AppConfig::default()));
let dispatcher = Dispatcher::new(app.clone(), DispatcherConfig::default(), "replica-1");
let shutdown = CancellationToken::new();
tokio::spawn(dispatcher.run(shutdown.clone()));
let inbox = InboxWorker::new(app.clone(), InboxConfig::default(), "replica-1");
tokio::spawn(inbox.run(shutdown.clone()));
```

## Features and environment

No Cargo features. The crate reads no environment variables; the binary maps
`DISPATCHER_CONCURRENCY`, `OUTBOX_LEASE_SECS` and friends onto
`DispatcherConfig`, and `INBOX_LEASE_SECS`, `INBOX_POLL_SECS`,
`INBOX_PARKED_TTL_SECS` and `INBOX_MAX_ATTEMPTS` onto `InboxConfig` (see
[`orchestrator`](../../bin/orchestrator/README.md)).

## Tests

Offline: they use the in-memory implementations of `orch-ports` (feature
`testkit`). No environment variables.

* `tests/service.rs`: the thread service without a dispatcher (validation,
  isolation between users, streams, idempotency, consumer-chosen thread ids and their collisions, `submit`; `list_agents` reads live cards,
  fails closed and keeps display order (static agents first), so the first agent stays the default; `describe_agent` is one agent with its card, live, `None` card when unreadable; `export_thread` is the thread, its binding and the whole log in order across the store's pages, bounded by `max_export_events` and `max_export_bytes` and flagged when either cuts, and someone else's thread is `NotFound`).
