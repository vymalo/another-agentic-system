# Mobile release

The Android and iOS targets under `src-tauri/gen/` are generated by Tauri 2 and
embed the same static web export as the desktop application. Android ships one
arm64 App Bundle to Google Play's **internal** track; iOS ships one arm64 IPA to
TestFlight. Windows has no mobile or desktop release path.

The native targets claim only `https://agentic.servers.segning.pro/mobile/auth/callback` through the exact-pinned Tauri
deep-link plugin (`tauri-plugin-deep-link = 2.6.1`). Android App Links and iOS Universal Links deliver that callback to the
webview as the plugin's deep-link event; the web page validates its PKCE `state` and exchanges the code. The existing native
`open_in_browser` command opens mobile authorization and logout URLs only after proving they have the build-time issuer origin.
No deep link is itself accepted as authentication.

`mobile-release.yml` runs when release-please publishes the same `vX.Y.Z` GitHub Release.
Release-please remains the only component allowed to create tags and GitHub
Releases. `flutter-tools/actions/release-cut` is therefore deliberately not
used: it would cut another tag and competing GitHub Release. The workflow uses
the compatible, platform-agnostic flutter-tools `artifact-upload`,
`play-submit`, and `testflight-submit` actions after Tauri builds the native
packages.

## Store setup and secrets

The release GitHub App must be installed on this repository with **Contents:
read and write**. Its `RELEASE_PLEASE_APP_CLIENT_ID` and
`RELEASE_PLEASE_APP_PRIVATE_KEY` secrets upload the completed AAB and IPA to the
GitHub Release which release-please already opened.

Android requires these repository secrets, except for the alias:

- `ANDROID_KEYSTORE_BASE64`: base64 of the private upload `.jks` file.
- `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_PASSWORD`: the two keystore
  passwords.
- `ANDROID_KEY_ALIAS`: the key alias (a repository variable, not a secret).
- `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON_BASE64`: a base64 Google Play service
  account key with permission to release to the internal track.

The bundle ID and Play package are `com.vymalo.agentic`. Create the Play Console
app and grant that service account internal-track access before the first
automated upload.

iOS requires:

- `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_API_KEY_BASE64`: an App Store Connect
  API key ID, issuer ID, and the base64 `.p8` private key.

The workflow presents these to Tauri as `APPLE_API_KEY`, `APPLE_API_ISSUER`, and
`APPLE_API_KEY_PATH` for Xcode automatic signing, then passes the resulting IPA
to flutter-tools' TestFlight upload. The Apple Developer account must own the
`com.vymalo.agentic` identifier, and the App Store Connect app must exist before
the first upload.

Every release-published run requires a strict `vX.Y.Z` tag. Release-please's
GitHub App is the publisher used by this repository: its bot login must match the
`RELEASE_PLEASE_APP_SLUG` repository variable. Protect release/tag creation
accordingly. The workflow then always submits the signed Android bundle to Play
internal testing and the signed iOS IPA to TestFlight.

The Android and iOS app builds set `AGENTIC_SIGN_IN=claimed` and use their own
public clients (`another-agentic-android` and `another-agentic-ios`). Desktop
builds retain loopback sign-in.

## Local builds

Install Android Studio (SDK, NDK, and JDK) for Android, or Xcode for iOS. Then:

```sh
cd apps/tauri
pnpm install
pnpm build:web
pnpm tauri android build --aab --target aarch64
pnpm tauri ios build --export-method app-store-connect
```

Android release signing reads the ignored
`src-tauri/gen/android/keystore.properties`; the CI workflow writes it from
secrets. Do not commit that file or a keystore. iOS release signing requires an
Apple Developer account and either Xcode automatic signing or the equivalent
manual signing credentials.

## Current product boundary

The web mobile OAuth flow validates the callback's `state` and exchanges the
code. Device-level App Links and Universal Links validation, live-store
delivery, and the static web export's streaming behavior in Android and iOS
webviews remain unverified.
