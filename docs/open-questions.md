# Open questions

Things not yet verified or decided. Each should be closed by an experiment or
an ADR, not by assumption.

| 27 | **Trace context across the outbox.** A W3C `traceparent` would follow a user request through the API, the outbox row, the worker's A2A call and back, but the outbox has no column for it and there is no OpenTelemetry exporter. | 28 | **Retention of the local agents' journal.** Runs and journal rows in `orch_agent_runs` and `orch_agent_journal` are kept for ever. adam-rs's `Store::purge_finished(agent, before)` exists (batches of 500 runs with their journals), but nothing in the orchestrator calls it. | The tables grow with every local task, in the database that also holds the chat log. | Decide the age and who runs it (a worker on a timer, or a job), then call `purge_finished` per kind; do it before a local agent with a long journal, such as the coder, ships. |
| 29 | **Inbox retention.** `applied`, `expired` and `dead` inbox rows are kept forever: they are what makes a redelivered webhook a duplicate (`UNIQUE (source, idempotency_key)`), and the `watches` rows are never removed. | The tables grow with every CI report, every timer and every pushed commit; deleting a row early makes a late redelivery look new. | Choose a retention window longer than any sender redelivers for (how long GitHub and the CI systems retry is *unverified*), purge in the inbox worker's pass, and add an index on the finished rows; then note it in [ADR 0016](decisions/0016-inbox-timers-and-job-ledger-on-the-thread.md#built-in-slice-5). Watches can go with their thread's finished job. |
| 30 | **A watch key shared by two threads.** `ci:<repo-key>@<sha>` names a commit, and two threads can push the same one (an empty change on the same base). The first thread to insert the key keeps it ([`Commit.watches`](../orchestrator/crates/ports/README.md)); the second never hears the CI report (the Postgres store logs a warning naming both threads). | A job would wait for CI until its deadline for no visible reason. | Decide between first wins (today), a watch per thread (`PRIMARY KEY (key, thread_id)` and one input per watcher), or refusing the second at push time; needs a real case to choose. |
| 31 | **A gate per job.** A thread's gate is fixed when it is created and every job of the thread runs under it ([ADR 0020](decisions/0020-a-thread-is-a-conversation.md)). | A follow-up cannot ask for a stricter or looser gate (for instance "open a pull request this time") than the thread's first message did. | Decide whether a run that starts a job may carry `vymalo.gate` (and what it may change: only add sources, as per thread today), and what `Job::next()` then keeps. Until then the gate is the thread's. |
| 32 | **CI facts across jobs on the same commit.** Two jobs of a thread that push the same commit (an empty change on the same base, or a follow-up that pushes nothing new) share its watch key `ci:<repo-key>@<sha>`; a CI report that arrived during job *n* is a card in the log but is not in job *n+1*'s ledger. | Job *n+1* under a `ci` gate waits for a report that GitHub will not send again for a commit it has already checked, and ends in `ci_timeout`. | Decide whether the new job re-asks the provider, or carries the facts about its pushed commit over when the commit is the same (the core already keeps facts about the commit it pushed across a rework). Related: #30. |
| 33 | **A follow-up sent as the task completes.** A message sent while a job is open is a delegation; if it is *sent* (a new A2A task) at the instant the first task completes, the thread goes `done` while the second task is running and the second task's updates are dropped as late (`InvalidInState`). The redelivery of ADR 0020 covers a delegation that had not been sent yet, not one that was. | The agent works on the message and the chat never shows it, until the person writes again. | When the dispatcher's `send_stream` returns a task different from the binding's on a thread that has become terminal, apply a redelivery that starts the next job **without** sending again (an input variant with no `Delegate`), and follow that task. A related gap: a redelivered message (ADR 0020) on a thread that moved on joins the job it reached, so two messages can reach the agent out of the order they were written in. |
| 37 | **Notification consent and delivery.** The person opts in at first open; the agent is told it may notify later about that chat. Open: the channel (Web Push or other), where a push subscription is stored (it is neither job ledger nor event log, ADR 0001), how an agent asks for a notification after its task ended, and how consent is withdrawn. | Notifications outside the chat touch privacy and ADR 0001's storage rule. | An ADR before the Notification opt-in component is built. |
| 38 | **Web view (iframe) and images in text.** Which origins may be framed, with which `sandbox` flags and Content-Security-Policy `frame-src`; whether remote images (and tool icons) are fetched directly, proxied, or only from allowed hosts. ADR 0013 rule 5 does not fetch remote images today. | A framed page or an image can track the person or phish inside the chat. | A Content-Security-Policy ADR (named as separate in ADR 0013) before the Web view and Image components. |
| 41 | **Where do devcontainers run on Kubernetes?** The coder builds a repository's devcontainer against a rootless Podman service beside it, one service per workspace volume ([ADR 0028](decisions/0028-devcontainer-json-is-the-workspace-environment-contract.md)). On Kubernetes the coder stays as it is: commands run in its own container, the Helm chart keeps `DEVCONTAINER_RUNTIME=off`, and a repository's devcontainer is ignored with a visible step. | Sandboxes and runtimes are the platform's concern ([ADR 0007](decisions/0007-protocol-only-dependencies.md), moved questions 2 and 7), and the platform is design only (*verified 2026-10-01*, its `CLAUDE.md`). Otherwise decide whether a deployment may run a Podman service per coder in a pod. Then a status note on ADR 0028. |

| 3 | opencode speaks its own API, not A2A — who writes the wrapper? | The agent host's harness: another-agentic-platform runs ADK-Rust (A2A via `adk-server`) driving `opencode acp` over stdio in the same Pod. |
| 8 | **Where does verification run?** Real CI (GitHub checks arriving by webhook) or a verifier agent over A2A? | Answered 2026-09-30 by [ADR 0018](decisions/0018-verification-gate-and-rework-loop.md) (built for the agent's own checks and for the verifier agent; CI is refused by configuration until its slices): both, and a third, chosen by configuration. The gate can require CI on the pushed commit ([ADR 0017](decisions/0017-ci-results-by-webhook.md): a GitHub webhook or a generic signed one), the checks the agent reports itself, and a verifier A2A agent, in any combination; the default gate is empty (today's behaviour). The proposal in the question, gate on real CI and allow a verifier for inner loops, is one configuration of it; a verifier never replaces a required CI. |
| 13 | **Implicit answers.** Is a new user message on a blocked thread without `resume` an answer, or rejected? | Answered 2026-09-29: it is accepted as the answer, as the question proposed. `translate` treats it as `Input::UserMessage` (tests `a_new_message_on_a_blocked_thread_without_resume_is_the_answer` in `orch-agui-projection` and `orch-surface-agui`), and the row is in the inbound table of [`api/agui.md`](api/agui.md#inbound-ag-ui--core-input). Revisit only if a client turns out to rely on rejection. |
| 14 | **Non-extending partial agent messages.** A partial `agent_message` that does not extend the previous text cannot be an AG-UI delta. | Answered 2026-09-29, in the projection and not in the A2A adapter as first proposed: a text that does not extend what was said closes the open message and starts a new one, message id `<id>~<seq>` (`Projector`, test in `orch-agui-projection` `projection.rs`); the same final message twice is said once. Documented under "Partial agent messages" in [`api/agui.md`](api/agui.md#outbound-log-event--ag-ui). |
| 19 | **Body limit on `/agui/agents/*`.** Standard clients POST the whole transcript. | Answered 2026-09-29: the AG-UI surface reads up to 8 MiB (`MAX_BODY_BYTES` in `orch-surface-agui`; a 2 MiB body is tested; over the limit is a 413 problem, see [`api/agui.md`](api/agui.md#run-binding)) and reconciles messages by id, so a client that re-sends the transcript works. The web sets `resumeTranscript: "appended"` (`use-chat-runtime.ts`) and sends only the new message or the `resume`; what that option does inside `@assistant-ui/react-ag-ui` was not re-read for this note (unverified). The resource API keeps its 1 MiB limit. |
| 34 | **Who coordinates a message that mentions several agents?** The addressed agent (calling the others through the orchestrator), a planner agent, or the orchestrator running an explicit sequence ([ADR 0026](decisions/0026-agent-mentions-as-structured-references.md), options A to D). | Answered 2026-10-01 on the owner's delegation ([ADR 0026](decisions/0026-agent-mentions-as-structured-references.md), status note): option A. The addressed agent asks the mentioned agents through the tool `ask_agent` of the orchestrator's per-thread MCP endpoint ([`api/thread-tools-v1.md`](api/thread-tools-v1.md)); each runs as a child task of the thread, nested under the step that asked, and its result returns to the tool call. A planner (B) can be added later. The owner may revisit it. |
| 35 | **Where do the credentials of attached MCP tools live?** Passed to the agent by reference (direct), or held by the orchestrator behind a per-thread MCP relay ([ADR 0024](decisions/0024-mcp-tools-attached-per-conversation.md)). Related: per-installation GitHub credentials (a GitHub App here, a PAT there), and #11. | Answered 2026-10-01 on the owner's delegation ([ADR 0024](decisions/0024-mcp-tools-attached-per-conversation.md), status note): the relay. The orchestrator holds the credentials of the servers the deployment lists and relays their tools on a per-thread MCP endpoint ([`api/thread-tools-v1.md`](api/thread-tools-v1.md)); the agent gets the endpoint and a short-lived, HMAC-signed token scoped to the thread, never written to the log or the outbox. Authentication beyond static credentials stays with #11. The owner may revisit it. |
| 36 | **Catalog versioning and the refetch seam.** The digest identifies a catalog ([ADR 0023](decisions/0023-ui-component-catalog-as-an-a2a-extension.md)); open: the refetch transport (a tool on the orchestrator's MCP surface or a URL in the extension's metadata, and how the agent authenticates), how long old digests are kept, and what an older UI does with a surface from a newer catalog. | Answered 2026-10-01 on the owner's delegation ([ADR 0023](decisions/0023-ui-component-catalog-as-an-a2a-extension.md), status note): the refetch is the tool `get_ui_catalog` on the per-thread MCP endpoint ([`api/thread-tools-v1.md`](api/thread-tools-v1.md)), authenticated by the thread-scoped token the agent gets with each message; every digest a thread saw stays in its log, the newest (highest `version`) is current and the refetch answers it; an older UI shows a visible "needs a newer version of the app" placeholder for a component it lacks ([`api/ui-catalog-v1.md`](api/ui-catalog-v1.md)). The test with one thread in two UI versions belongs to MVP slice 3. The owner may revisit it. |
| 39 | **The registry format with the platform.** A2A standardises no registry API (*verified 2026-10-01*, <https://a2a-protocol.org/latest/topics/agent-discovery/>). The candidate is an `api-catalog` linkset listing one agent card per agent service ([ADR 0022](decisions/0022-platform-provisions-agents-system-discovers-them.md)); open: the format, its URI and version, authentication, and how tags and releases appear. | Answered 2026-10-01 on the owner's delegation ([ADR 0022](decisions/0022-platform-provisions-agents-system-discovers-them.md), status note): `agent-registry/v1` (URI `https://agents.vymalo.com/registry/v1`), a contract in another-agentic-platform ([`docs/extensions/agent-registry-v1.md`](https://github.com/vymalo/another-agentic-platform/blob/main/docs/extensions/agent-registry-v1.md), [#8](https://github.com/vymalo/another-agentic-platform/pull/8)): an RFC 9727 `api-catalog`-shaped linkset with one agent-card URL per agent service, its id and optional `tags` (labels for display and filtering, not releases); releases (and their channel tags) stay on each card; a bearer token for now (#11). The mock is in compose (MVP slice 9). The owner may revisit it. |
