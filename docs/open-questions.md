# Open questions

Things not yet verified or decided. Each should be closed by an experiment or
an ADR, not by assumption.

| 6 | **Budgets:** attempts, wall clock and tokens per job and per step. | Multi-agent loops can burn tokens silently. The orchestrator owns attempts and wall clock; tokens are spent by agents and measured by their gateways. | ADR once gateway usage data (EAIG / AISIX) is reachable. Status 2026-09-30: partly answered by [ADR 0018](decisions/0018-verification-gate-and-rework-loop.md) (planned, not built). **Attempts** are decided: 3 by default, configurable, capped at 10 (`ORCH_MAX_ATTEMPTS`, `ORCH_MAX_ATTEMPTS_CAP`), and a job that spends them ends `Failed` with the findings. **Wall clock** is decided only for the waits on CI (`ORCH_CI_TIMEOUT_SECS`, 3600) and on the verifier (`ORCH_VERIFIER_TIMEOUT_SECS`, 1800), each ending in `Blocked` without spending an attempt; there is no wall-clock budget for a job or a step. **Tokens** are not decided. Stays open. |

| 24 | **Workspace placement for agents with a filesystem.** ADR 0015 decided in principle that the deployer picks: `Shared` (RWX volume), `Affinity` (a worker owns a run's folder), `Isolated` (per-worker PVC, implies affinity), or none (A2A only). The runtime has no run-to-worker affinity today. | Per-worker volumes need a run to return to its worker; until then a coder deployment runs one worker or a shared volume. | Design the closed enum and the lease mechanism in adam-rs; then an ADR there, and a note here ([ADR 0015](decisions/0015-control-plane-and-workers-on-adam-rs.md)). |

Status 2026-09-30: the payload limit is verified, `MAX_PAYLOAD_BYTES = 7_999` in `adam-notify-postgres` at `882e239` ([ADR 0015](decisions/0015-control-plane-and-workers-on-adam-rs.md), status note 2026-09-30); the local agents use that notifier on the channels `orch_agent_events` and `orch_agent_signals`. |
| 26 | **Local agents: schema and the `all` role.** Who owns the `orch_agent_*` migrations and their retention, and may `all` (one process with the API) host a tool-running local agent? | The journal is part of the job ledger; in `all`, a build can starve the API (lesson 1). | Decide before the first local agent ships (PR 12 of the ADR 0015 order). Status 2026-09-30: the journal is in the orchestrator's Postgres (owner's decision), `LocalAgents::migrate` creates it at boot in every role, and retention is question 28. What stays open is the `all` role for a tool-running local agent, which waits for the coder kind. |
| 27 | **Trace context across the outbox.** A W3C `traceparent` would follow a user request through the API, the outbox row, the worker's A2A call and back, but the outbox has no column for it and there is no OpenTelemetry exporter. | 28 | **Retention of the local agents' journal.** Runs and journal rows in `orch_agent_runs` and `orch_agent_journal` are kept for ever. adam-rs's `Store::purge_finished(agent, before)` exists (batches of 500 runs with their journals), but nothing in the orchestrator calls it. | The tables grow with every local task, in the database that also holds the chat log. | Decide the age and who runs it (a worker on a timer, or a job), then call `purge_finished` per kind; do it before a local agent with a long journal, such as the coder, ships. |

## Closed

| # | Question | Resolution |
|---|---|---|
| 3 | opencode speaks its own API, not A2A — who writes the wrapper? | The agent host's harness: another-agentic-platform runs ADK-Rust (A2A via `adk-server`) driving `opencode acp` over stdio in the same Pod. |
| 8 | **Where does verification run?** Real CI (GitHub checks arriving by webhook) or a verifier agent over A2A? | Answered 2026-09-30 by [ADR 0018](decisions/0018-verification-gate-and-rework-loop.md) (planned, not built): both, and a third, chosen by configuration. The gate can require CI on the pushed commit ([ADR 0017](decisions/0017-ci-results-by-webhook.md): a GitHub webhook or a generic signed one), the checks the agent reports itself, and a verifier A2A agent, in any combination; the default gate is empty (today's behaviour). The proposal in the question, gate on real CI and allow a verifier for inner loops, is one configuration of it; a verifier never replaces a required CI. |
| 13 | **Implicit answers.** Is a new user message on a blocked thread without `resume` an answer, or rejected? | Answered 2026-09-29: it is accepted as the answer, as the question proposed. `translate` treats it as `Input::UserMessage` (tests `a_new_message_on_a_blocked_thread_without_resume_is_the_answer` in `orch-agui-projection` and `orch-surface-agui`), and the row is in the inbound table of [`api/agui.md`](api/agui.md#inbound-ag-ui--core-input). Revisit only if a client turns out to rely on rejection. |
| 14 | **Non-extending partial agent messages.** A partial `agent_message` that does not extend the previous text cannot be an AG-UI delta. | Answered 2026-09-29, in the projection and not in the A2A adapter as first proposed: a text that does not extend what was said closes the open message and starts a new one, message id `<id>~<seq>` (`Projector`, test in `orch-agui-projection` `projection.rs`); the same final message twice is said once. Documented under "Partial agent messages" in [`api/agui.md`](api/agui.md#outbound-log-event--ag-ui). |
| 19 | **Body limit on `/agui/agents/*`.** Standard clients POST the whole transcript. | Answered 2026-09-29: the AG-UI surface reads up to 8 MiB (`MAX_BODY_BYTES` in `orch-surface-agui`; a 2 MiB body is tested; over the limit is a 413 problem, see [`api/agui.md`](api/agui.md#run-binding)) and reconciles messages by id, so a client that re-sends the transcript works. The web sets `resumeTranscript: "appended"` (`use-chat-runtime.ts`) and sends only the new message or the `resume`; what that option does inside `@assistant-ui/react-ag-ui` was not re-read for this note (unverified). The resource API keeps its 1 MiB limit. |
